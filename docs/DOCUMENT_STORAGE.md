# Хранение документов на сервере ЧелГУ

## 1. Что хранится

Система создаёт два вида файлов:

1. **Корпус судебных решений** — исходные тексты `parsed_texts/*.txt`,
   FAISS-индекс, BM25 и метаданные чанков. Это общедоступные судебные акты,
   персональных данных в них минимум, но встречаются ФИО и адреса.
2. **Черновики процессуальных документов** — то, что пользователь ввёл в форму
   и получил в DOCX. Здесь могут быть ФИО, адреса, суммы, номера дел. Это
   персональные данные, и хранить их нужно осознанно.

Корпус и черновики лежат в разных каталогах и имеют разные права доступа.

## 2. Вариант для одного сервера (реализован в проекте)

```
/var/lib/legal-assistant/
├── parsed_texts/            # корпус, доступ на чтение приложению
├── document_index.faiss
├── chunks_data.pkl
├── bm25_index.pkl
├── query_logs.db            # логи запросов
└── stored_documents/        # черновики пользователей
    └── 2026/11/
        ├── <uuid>.docx
        └── <uuid>.json      # метаданные: заголовок, тип, время, sha256
```

Включается в `.env`:

```dotenv
DOCUMENTS_ENABLED=true
DOCUMENTS_DIR=/var/lib/legal-assistant/stored_documents
DOCUMENTS_MAX_MB=10
DOCUMENTS_RETENTION_DAYS=90
ADMIN_TOKEN=<токен>
```

Права:

```bash
sudo install -d -o legal -g legal -m 750 /var/lib/legal-assistant/stored_documents
sudo chmod 640 /var/lib/legal-assistant/stored_documents/*/*/*.json
```

Приложение пишет файл во временный `.tmp`, вызывает `fsync` и только затем
`os.replace`. Поэтому при отключении питания не остаётся полузаписанных DOCX.
Имя файла — UUID, заголовок хранится только в JSON: это исключает path
traversal и конфликты имён.

### API

| Метод | Путь | Доступ | Назначение |
| --- | --- | --- | --- |
| POST | `/api/documents/save` | админ-токен | сохранить DOCX и метаданные |
| GET | `/api/documents/saved` | админ-токен | список с пагинацией |
| GET | `/api/documents/saved/{id}` | админ-токен | скачать DOCX |

Пример:

```bash
curl -X POST https://pravo.chelgu.ru/api/documents/save \
  -H "X-Admin-Token: $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Исковое заявление","text":"...","document_type":"claim"}'
```

Возвращается `id`, `created_at`, `size_bytes`, `sha256`. Хеш позволяет
проверить целостность при восстановлении из резервной копии.

### Срок хранения

`DOCUMENTS_RETENTION_DAYS=90` — разумный срок по умолчанию для учебного сервиса.
Очистка запускается вручную или по cron:

```bash
cd /opt/legal-assistant
.venv/bin/python -c "import document_store; print(document_store.cleanup_expired())"
```

Для юридически значимых документов срок может быть больше; решение принимает
Институт права, а не разработчик.

## 3. Вариант для нескольких серверов

Если приложение будут запускать на нескольких узлах или понадобится резервный,
локальный каталог заменяется на общий ресурс без изменения кода:

### Вариант A. NFS с файлового сервера вуза

```
nfsserver:/export/legal-assistant/documents -> /var/lib/legal-assistant/stored_documents
```

Плюсы: минимум изменений, привычная инфраструктура. Минусы: блокировки и
задержки при записи, единая точка отказа. Монтировать с `hard,intr`, включить
бэкап на стороне файлового сервера.

### Вариант B. S3-совместимое хранилище (MinIO в контуре вуза)

Рекомендуется при росте нагрузки:

- бакет `legal-documents`, версионирование включено;
- ключи доступа только у приложения;
- объекты шифруются на стороне сервера (SSE-S3);
- `document_store.py` заменяется адаптером с теми же функциями
  `save_document/list_documents/get_document`;
- срок хранения — lifecycle policy (например, 365 дней).

### Вариант C. База данных

DOCX можно хранить как BLOB в PostgreSQL. Плюс — транзакционность и единый
бэкап; минус — раздувание БД и сложнее отдавать файлы. Для сотен документов
в месяц подходит, для десятков тысяч — нет.

## 4. Резервное копирование

Минимальная схема:

| Что | Частота | Куда | Срок |
| --- | --- | --- | --- |
| `stored_documents/` | ежедневно, 02:00 | NAS вуза, шифрованный архив | 30 дней |
| `query_logs.db` | ежедневно | NAS | 30 дней |
| индексы | после переиндексации | NAS | 2 версии |
| `.env` и конфиги | при изменении | менеджер секретов | постоянно |

Пример:

```bash
#!/usr/bin/env bash
set -euo pipefail
DAY=$(date +%F)
tar -czf "/backup/legal-documents-$DAY.tar.gz" \
  -C /var/lib/legal-assistant stored_documents
gpg --encrypt --recipient legal-backup@chelgu.ru \
  "/backup/legal-documents-$DAY.tar.gz"
rm "/backup/legal-documents-$DAY.tar.gz"
```

Проверка восстановления — раз в квартал: развернуть архив в тестовый каталог,
сверить `sha256` из JSON и открыть DOCX.

## 5. Правовые и организационные требования

1. **152-ФЗ.** Черновики содержат персональные данные. Нужны:
   согласие пользователя на обработку, ограничение доступа, срок хранения,
   журнал доступа, ответственное лицо в Институте.
2. **Локализация.** Данные не должны уходить за пределы контура вуза.
   Поэтому LLM — локальная (Ollama/vLLM), без внешних API.
3. **Минимизация.** Не сохраняйте документ автоматически. Сохранение —
   отдельное осознанное действие пользователя (кнопка/API), по умолчанию
   выключено.
4. **Обезличивание логов.** Текст запроса в `query_logs` можно заменять
   хешем или категорией после анализа.
5. **Аудит.** Каждое скачивание из админки желательно логировать в отдельный
   файл: кто, когда, какой `id`, с какого IP.

## 6. Что сделать при развёртывании

- [ ] Создать каталог `/var/lib/legal-assistant/stored_documents`, владелец `legal:legal`, права 750.
- [ ] Включить `DOCUMENTS_ENABLED=true` только после настройки `ADMIN_TOKEN`.
- [ ] Настроить ежедневный бэкап и проверить восстановление.
- [ ] Ограничить доступ к `/api/documents/saved*` на nginx (SSO или allowlist).
- [ ] Утвердить срок хранения и порядок удаления.
- [ ] Добавить в политику конфиденциальности пункт о хранении черновиков.
